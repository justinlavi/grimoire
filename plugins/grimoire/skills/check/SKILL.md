# Grimoire Directory Guard

How a command finds the grimoire it acts on, and how it learns whether it may change that
grimoire. Resolve `GRIMOIRE_ROOT` before you read or change any grimoire content.

1. Read `~/grimoires/library.json` and expand `$HOME` in each grimoire's `local_path`.
2. Apply the first row that matches the current working directory:

| Current working directory | Action |
|---|---|
| Equal to, or inside, a registered grimoire | Set `GRIMOIRE_ROOT` to that grimoire's root. |
| The framework root | Refuse, unless the user names a grimoire. |
| Elsewhere, and one grimoire is registered | Set `GRIMOIRE_ROOT` to it and tell the user which grimoire you selected. |
| Elsewhere, and several are registered | List them, ask which one to use, and continue after the user chooses. |
| Elsewhere, and none is registered | Stop. Tell the user to run `/grimoire:setup` to set one up. |

3. Stop when the active grimoire cannot be resolved without guessing.

The terminal does not have to `cd` into the grimoire. Use explicit paths:

- Rites: pass `--grimoire GRIMOIRE_ROOT`.
- File reads and writes: use paths under `GRIMOIRE_ROOT`.
- A command that needs a working directory: set it to `GRIMOIRE_ROOT`.

## Before a command changes the grimoire

A grimoire joined from a link is registered for reading on this computer (`"access": "read"` in
its library entry): updates keep it current, and no command changes its files. `/grimoire:add`,
`/grimoire:save`, `/grimoire:move`, `/grimoire:remove`, `/grimoire:check fix` and `/grimoire:publish init` change files, so
each of them first runs `~/.grimoire/bin/grimoire grimoire_access --grimoire GRIMOIRE_ROOT --format json`:

- `summary.access` is `edit`: continue.
- `summary.access` is `read`: say that this copy is set up for reading, and ask once whether to
  switch it to editing. On yes, run the same command with `--set edit --apply`, confirm that
  `summary.access` is `edit`, and continue. On no, stop; nothing changed.

The switch changes one field of the library entry. The host of the grimoire decides whether the
user may share changes; `/grimoire:save` reports a refused push. A rite that reports `status: blocked`
with `summary.access` `read` met this rule: apply it.

# Invocation: Check

Answer the question "is my grimoire in good shape?". With no scope, run the full health pass: the
mechanical validators, then the judgment passes that keep a grimoire honest as it grows (stale
claims, ghost references, contradictions, missing cross-references). A scope narrows the run to the
validators, to a naming review, to a boundary review, or to the mechanical link repairs.

## Trigger

```
/grimoire:check                   # full health pass
/grimoire:check quick             # mechanical validators only
/grimoire:check <validator> ...   # one or more validators, by selector
/grimoire:check smart | auto | summary | parallel
/grimoire:check naming            # judgment review of names, terminology, discoverability
/grimoire:check boundaries        # judgment review of system words in a grimoire's content
/grimoire:check fix               # apply the mechanical repairs (wikilink promotion and casing)
```

`--since <window>` sets the stale window of the full health pass (default: 90 days).
`--chapter=<name>` narrows `naming` to one chapter.

The user asks whether the grimoire is healthy or valid, or says "check the grimoire", "find
orphans", "fix wikilinks" or "audit naming". Run it before a save, after a batch of adds, and
periodically.

| A request that looks similar | Goes to |
|---|---|
| Validate the framework, or review its naming and vocabulary | `/grimoire-dev:validate`, `/grimoire-dev:improve` |
| Rename or move a page after a naming finding | `/grimoire:move` |
| Learn what a website would expose | `/grimoire:publish check` |

## Inputs

- `GRIMOIRE_ROOT`, resolved by the [[invocations/meta/grimoire_directory_guard|grimoire directory guard]].
  The grimoire must have `chapters/` and a root hub. This playbook acts on the active grimoire only.
- The first positional argument (the scope) and the options above.
- [[invocations/validators/validators|validators]], which lists every selector with its rite and
  what it checks. `/grimoire:check` accepts the selectors of the `grimoire` profile.
- The output of the rites this playbook runs: `validate`, `repair_links`, `recent_changes`.
- `naming` in `GRIMOIRE_ROOT/grimoire.json` (`snake_case` when absent), for the `naming` scope.
- "The Magical Boundary" in [[docs/reference|reference]], for the `boundaries` scope.

## Never

- Never override a rite's output. The validators are the source of truth for structure,
  frontmatter, link, orphan and provenance findings; a judgment that contradicts them is a guess.
- Never resolve a contradiction or a stale claim silently. Surface it. Which claim is true is
  knowledge the user holds, and a silent fix can erase the correct one.
- Never update `last_verified` without verifying the page. The date records that a person or an
  assistant checked the page's claims.
- Never guess the target of an ambiguous or missing wikilink, and never fabricate a target. A wrong
  link routes every later reader to the wrong page.
- Never run `repair_links --apply` before the user has seen the dry run and approved it.
- Never write a file during the `naming` or `boundaries` scope unless the user asks. Both report
  in chat.

## Steps

### 1. Resolve the grimoire

Apply the grimoire directory guard and set `GRIMOIRE_ROOT`.

- Done when: `GRIMOIRE_ROOT` is set, and `GRIMOIRE_ROOT/chapters/` and the root hub exist.
- Stop when: `chapters/` or the root hub is missing. Report which one, and end.

### 2. Route on the scope

Read the first positional argument and run only the matching section:

| Argument | Section |
|---|---|
| none | Scope: none (the full health pass) |
| `quick`, `smart`, `auto`, `summary`, `parallel`, or validator selectors | Scope: validators |
| `fix` | Scope: `fix` |
| `naming` | Scope: `naming` |
| `boundaries` | Scope: `boundaries` |

- Done when: one section is selected.

### Scope: validators

#### 1. Run the selected validators

```bash
~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT            # quick: the full mechanical suite
~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT links frontmatter
~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT smart     # which validators the current git changes need
~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT auto      # run those
~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT summary
~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT parallel
```

Pass the user's selectors through unchanged. Report the failed validators, with their diagnostics
grouped by file and line.

- Done when: the rite exits 0 (the selected validators passed) or 1 (one or more failed), and the
  user has the result.
- Stop when: the rite exits 2. The selector is not in the grimoire profile, or two modes conflict;
  show the selectors the rite lists and ask which the user meant.

### Scope: none (the full health pass)

Steps 2 to 5 are independent read-only scans. When, and only when, the assistant can spawn
subagents, run them as the parallel lanes `stale-claims`, `ghost-references`, `contradictions` and
`missing-cross-refs`, by the protocol in [[invocations/meta/subagent_lanes|subagent lanes]];
otherwise run them in order. A lane surfaces and proposes. The orchestrator always runs steps 1, 6,
7, 8 and 9.

#### 1. Run the mechanical validators

```bash
~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT
```

Capture the output.

- Done when: the rite has exited and you hold its diagnostics.
- Stop when: `structure` or `frontmatter` reports errors. They invalidate the later steps; report
  them and end the pass.

#### 2. Find stale claims

For every page whose `last_verified` is older than the stale window, list the page, its
`last_verified` and its chapter. Categorize it: critical (a hub links to it), normal (a leaf), or
historical (it carries the `status/deprecated` tag).

- Done when: every page past the window is listed with a category. Surface the list; change no
  date.

#### 3. Find ghost references

Scan the chapter pages for entity-shaped tokens: capitalized phrases, code identifiers, recurring
proper nouns. For each token that appears in three or more pages and has no page of its own,
propose a page, with the token's frequency and the pages that mention it.

- Done when: every such token is listed. The user picks which ones become pages.

#### 4. Find contradictions

Compare the pages that share tags, especially the same `chapter/<chapter>` tag, and look for
opposing claims: numerical (different numbers for the same thing, such as version numbers or
counts), procedural (different steps for the same task), definitional (different meanings for one
term). Report each contradiction as one finding that names both pages and both claims, with
`file:line` citations.

- Done when: every pair of pages with a shared tag has been compared, and each contradiction is a
  finding that cites both pages. Leave the resolution to the user.

#### 5. Find missing cross-references

For each pair of pages in the same chapter, or sharing a `domain/<...>` tag, that discuss the same
entity or concept, make sure each links to the other. Suggest the full-path wikilinks that close
each gap.

- Done when: every such pair either links both ways or has a suggested pair of wikilinks.

#### 6. Apply fixes with the user

Group the findings into three categories and ask the user about each:

| Category | Findings | Action |
|---|---|---|
| Apply | Clearly mechanical fixes: broken links the rite located, missing wikilinks whose target exists, frontmatter format errors. Wikilink promotion follows the `fix` scope. | Apply them. |
| Confirm, then apply | Orphan wiring (which hub should own the orphan?), terminology standardization, page promotions | Ask about each one, then apply. |
| Surface only | Contradictions, stale claims, ghost references | List them. Act only on explicit approval. |

- Done when: every finding is applied, declined or listed, and you hold the list of pages you
  changed.

#### 7. Relate the findings to recent changes

```bash
~/.grimoire/bin/grimoire recent_changes --grimoire GRIMOIRE_ROOT --since 90d
```

Relate the findings to the recent edits the rite lists.

- Done when: the rite printed its table, or printed `no history` because the grimoire is not a git
  repository. Report `no history` plainly; do not invent a timeline.

#### 8. Validate again

Run the command of step 1 again.

- Done when: the rite exits 0. The pass is not complete before it does.
- Stop when: a diagnostic remains that needs a decision about content. Report it with its file and
  line.

#### 9. Report

Give the health report, and list every page changed in step 6.

| Category | Count | Status |
|---|---|---|
| Structure errors | n | pass/fail |
| Frontmatter violations | n | pass/fail |
| Broken links / wikilinks | n | pass/fail |
| Orphans | n | listed |
| Provenance violations | n | listed |
| Stale (past window) | n | listed |
| Ghost references | n | listed |
| Contradictions | n | listed |
| Missing cross-refs | n | listed |
| Fixes applied | n | itemized |

- Done when: the user has the table, the findings behind each row and the list of changed pages.

### Scope: `fix`

The rite `rites/repair_links.py` makes two repairs, on the pages the link validator checks (not
`publish/` and not chapter-local `sources/` wrappers). It promotes a filename-only wikilink (`[[foo]]`,
`[[parent_sibling|sibling]]`) to the full-path form (`[[chapters/path/to/foo|foo]]`), and it
respells a full-path wikilink whose casing differs from the file on disk. The grimoire should be
under version control, so that the change can be reviewed as a diff.

#### 1. Dry run

```bash
~/.grimoire/bin/grimoire repair_links --grimoire GRIMOIRE_ROOT
```

The run writes nothing and prints four sections:

| Section | Lines | Meaning |
|---|---|---|
| Repairs | `[FIX]`, `[CASE]` | One unambiguous target; `--apply` rewrites the link |
| Ambiguous | `[AMBI]` | Several candidates, or only the display label names a page; the rite never guesses |
| Unresolvable | `[MISS]`, `[SKIP]` | No file matches, or the link is a partial path the rite leaves alone |
| Skipped | `[SKIP]` | The link looks like a template placeholder |

The rite tries, in order: a sibling in the source directory, a unique descendant of that directory,
a unique descendant of the source chapter, a unique match under `chapters/`. When the link's own name matches no file but its display label
names one, the link is reported as ambiguous and left alone. It skips code fences and inline code,
and a page that is not valid UTF-8 is listed as unreadable and left untouched.

- Done when: the rite exits 0 (nothing to repair) or 1 (repairs or links that need attention).

#### 2. Review and get approval

Show the user the dry run. Check that bulk patterns resolve sensibly. Look at the ambiguous links where no candidate fits; the page may
need splitting or moving first.

- Done when: the user approves the repairs and the guard reports that the copy can be changed.
- Stop when: the user does not approve, or the copy stays set up for reading. Write nothing.

#### 3. Apply

```bash
~/.grimoire/bin/grimoire repair_links --grimoire GRIMOIRE_ROOT --apply
```

The rite keeps existing display labels and `#section` suffixes, and adds the filename as the label
where a link has none (except in a table row).

- Done when: the rite exits 0.

#### 4. Resolve what the rite left

For each `[AMBI]` line, open the source line, read the surrounding paragraph, and edit the wikilink
to the full path that is meant. For each `[MISS]` line the target does not exist: delete the
reference, file a page, or fix the typo.

- Done when: every `[AMBI]` and `[MISS]` line is resolved or reported as left open.
- Stop when: the paragraph does not settle which page is meant. Ask the user.

#### 5. Validate again

```bash
~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT links orphans
```

The orphan count should drop as reconnected pages rejoin the routing graph. Report the files
touched, the repairs made, the ambiguities resolved, the misses left open, and the broken-link
counts before and after.

- Done when: the user has that report and the exit code of the validators.

### Scope: `naming`

A judgment review: are chapter and file names clear, discoverable, consistent in their terms and
economical to read? No validator reads meaning in a grimoire; this review does. With
`--chapter=<name>`, review that chapter only.

#### 1. Load the context

Read the root hub, the chapter list, and `GRIMOIRE_ROOT/docs/reference.md` when the grimoire has
one; it holds the grimoire's canonical vocabulary. Read `naming` from `grimoire.json`.

- Done when: you know the chapters and the recorded convention. When none is recorded, note the
  dominant pattern and propose recording it.

#### 2. Score each chapter and file name

Score each name on four dimensions, from 0 to 100 each, then grade it:

| Dimension | Judge |
|---|---|
| Specificity | Reward compounds from the subject's vocabulary. Penalize `misc`, `stuff` and names stamped with a version. |
| Searchability | Does the name use terms a user or an assistant would query, and is it reachable from a hub? |
| Comprehension | Is the name self-explanatory, with unambiguous abbreviations and the right level of jargon? |
| Token efficiency | The length of the name against the knowledge it holds, and the hops needed to reach it |

Grades: A (80-100) keep; B (70-79) optional polish; C (60-69) consider a rename; D (50-59) should
be renamed; F (below 50) must be renamed.

- Done when: every chapter and file name in scope has a score and a grade.

#### 3. Find terminology drift

Build a synonym map across names, headings and prose: `config` / `configuration` / `cfg`, `repo` /
`repository`, case variants. Pick one canonical form for each; the grimoire's `docs/reference.md`
decides when it exists. A filename that deviates from the recorded naming convention is an advisory
finding, never an error. Under `preserve`, imported casing is intentional and is not a finding.

- Done when: every group of synonyms has a canonical form.

#### 4. Test discoverability

For five to ten plausible queries, judge whether the number of hops is proportionate to the topic's
depth. Flag orphans, single points of failure (critical knowledge with one route in) and hot paths
buried behind extra hops.

- Done when: each query has a hop count and a verdict.

#### 5. Review the structure

Depth is open-ended. Flag nesting that narrows nothing, missed grouping, bloated chapters (split
candidates), tiny chapters (merge candidates), more than eight siblings under one hub, a parent
whose children do not belong together, and a hub with a single child (a collapse candidate).

- Done when: each flagged folder has a finding.

#### 6. Recommend

Group the recommendations by priority: critical renames (a score below 50), suggested renames
(50-69), terminology standardization, structure changes, and quick wins (under 30 minutes for a gain
of 10 points). For each rename give the current name, the proposed name, the files affected, what
breaks, the effort and the predicted gain. Propose names that are nouns or noun phrases, use the
subject's vocabulary over a casual paraphrase, carry no date or version, prefer clarity to brevity,
and follow the recorded naming convention.

Apply critical renames, terminology standardization and quick wins once the user confirms; make
each rename through [[invocations/grm/move|move]]. Weigh carefully a refactor of more than two
hours or a rename that touches more than ten files. Defer cosmetic changes and anything that
conflicts with a convention the user has set.

- Done when: the user has the three deliverables that Outputs lists for this scope.
- Stop when: a rename is not confirmed. Do not apply it.

### Scope: `boundaries`

A judgment review of the boundary between system words and a grimoire's content. Read "The Magical
Boundary" in [[docs/reference|reference]] first; it owns the first two rules below.

| Rule | Exception |
|---|---|
| No `invocations/`, `formulae/` or `rites/` folder in a grimoire | None |
| No system term (invocation, formula, rite, summoning) in chapter prose | Naming a framework command |
| No platform assumption in shared content: name the generic role, not the vendor | A page that documents an integration |
| No department word that assumes who the reader is | A grimoire whose subject is that department |
| Example names are generic: `Alice` and `Bob`, `Project Alpha` | A page that documents an integration |

`chapters/projects/` may name real platforms, teams, products and people.

#### 1. Scan

Run each command with `GRIMOIRE_ROOT` as the working directory.

1. System folders. Any hit is critical: rename the folder to its practical equivalent, or move real
   system logic to the framework.

   ```bash
   find . -type d \( -name invocations -o -name formulae -o -name rites \) -not -path './.git/*'
   ```

2. System terms in prose. Skip references to the framework itself; rewrite the rest in the
   subject's own words.

   ```bash
   grep -rniE 'invoke .*invocation|consult .*formula|perform .*rite|cast .*spell' chapters/ templates/ scripts/
   ```

3. Platform and department words outside `chapters/projects/`.

   ```bash
   grep -rniE '\b(Slack|Teams|Discord|SharePoint|Confluence|Google Drive|Jira|Bitbucket)\b' chapters/
   grep -rniE '\b(HR|Legal|Marketing|Sales|Finance)\b|\b(VP|Director|Manager) of\b' chapters/
   ```

4. Example names. Replace a real company, product or person used as an example with a generic
   name.

- Done when: the four scans have run and every hit is classified as a violation or an exception.

#### 2. Report

Report `Magical Boundary Compliance: PASS | FAIL` with a count for each of: system folders, system
terms, platform assumptions, department words, example names. For each violation give the file,
the line, the offending text, the fix and the severity: critical (a system folder in the grimoire),
warning (a system term, or an unwarranted platform or department word, in a shared chapter), or
info (an example name that could be more generic).

- Done when: the user has the verdict, the counts and the violations.

## Evidence and checks

- Mechanical findings cite the rite that produced them and its exit code. Counts in the health
  report come from the validators' output, never from your own tally of files.
- A judgment finding cites `file:line` for every page it names. A contradiction cites both pages.
- The full health pass and the `fix` scope report success only after
  `~/.grimoire/bin/grimoire validate --grimoire GRIMOIRE_ROOT` (or `links orphans` for `fix`)
  has run again; report its exit code as it is.
- Say which scans ran serially and which ran as lanes.

## Outputs

| Scope | Leaves |
|---|---|
| Validators | No file changes. The failed validators and their diagnostics, by file and line. |
| None | Only the fixes the user approved in step 6. The health report and the list of changed pages. |
| `fix` | Rewritten wikilinks in the files the rite touched, and the links edited by hand. The repair report. |
| `naming` | No file changes unless the user confirms a rename. In chat: the analysis report (grades, the top five and bottom five names, conflicts with the canonical forms, renames with their impact), the quick-wins list, and a terminology registry as JSON (canonical terms, abbreviations, scores per chapter). |
| `boundaries` | No file changes. The compliance report. |

Every reply leads with the outcome ("the grimoire is healthy", or the count of findings that need
a decision), then gives the one next action, then says what did not run.
